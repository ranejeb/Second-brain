# Local Second Brain (RAG & Knowledge Analytics)

Приватная система управления знаниями, семантического поиска по документам и аналитики текстовых данных. Проект работает полностью локально без передачи данных во внешние облачные сервисы.

---

## Архитектура и технологический стек

Система развёрнута в виде изолированных микросервисов под управлением **Docker Compose**:

* **Хранилище и векторный поиск:** `PostgreSQL 16` + расширение `pgvector` (хранение реляционных метаданных, JSONB-истории чатов и 768-мерных векторных эмбеддингов).
* **Инференс нейросетей:** `Ollama` (локальный REST API сервер для запуска моделей на CPU/GPU):
  * `nomic-embed-text` — генерация векторных представлений текста (размерность `768`).
  * `qwen2.5:3b` / `qwen2.5:0.5b` — генерация ответов на основе найденного контекста.
* **ETL и аналитика данных:** `Python 3.11`, `Pandas` (табличная обработка и расчёт текстовых метрик), `pypdf` (парсинг PDF), `psycopg 3` (драйвер БД).
* **Пользовательский интерфейс и визуализация:** `Streamlit` (веб-интерфейс, управление рабочими пространствами, потоковый вывод ответов) + `Plotly` (интерактивные графики).

## Математика и алгоритмы

### 1. Семантические эмбеддинги и косинусное сходство
Каждый текстовый фрагмент $A$ и поисковый запрос пользователя $B$ пропускаются через модель `nomic-embed-text` и преобразуются в векторы в евклидовом пространстве $\mathbb{R}^{768}$:

$$\mathbf{A} = (a_1, a_2, \dots, a_{768}), \quad \mathbf{B} = (b_1, b_2, \dots, b_{768})$$

Семантическая близость между запросом и фрагментом документа вычисляется в PostgreSQL с помощью оператора косинусного расстояния `<=>` (`vector_cosine_ops`):

$$\text{Cosine Similarity}(\mathbf{A}, \mathbf{B}) = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|} = \frac{\sum_{i=1}^{768} a_i b_i}{\sqrt{\sum_{i=1}^{768} a_i^2} \sqrt{\sum_{i=1}^{768} b_i^2}}$$

Косинусное расстояние вычисляется как $D_{\cos} = 1 - \text{Cosine Similarity}$, а итоговый процент совпадения в интерфейсе равен $1 - D_{\cos}$. Значение близкое к `1.0` (100%) означает максимальную смысловую близость.

### 2. Гибридный поиск (Hybrid Search)
Для компенсации потерь точных терминов при векторном сжатии применяется гибридное ранжирование на уровне SQL-запроса:
* Базовый скор формируется из косинусного сходства векторов.
* При наличии в запросе ключевых терминов (длина $\ge 4$ символов) выполняется регистронезависимый поиск подстроки (`ILIKE`). За точное лексическое совпадение начисляется бонус $+0.15$ к итоговой релевантности:

$$\text{Score} = \min\Big(1.0, \; (1 - D_{\cos}) + 0.15 \cdot \mathbb{I}(\text{keyword} \in \text{content})\Big)$$

* Для обзорных запросов по структуре документа автоматически приоритизируются начальные блоки (`chunk_index IN (0, 1, 2)`).

### 3. Чанкинг с перекрытием (Sliding Window Chunking)
Длинные документы разбиваются скользящим окном фиксированного размера ($L = 800$ символов) с перекрытием ($O = 150$ символов). Нахлёст предотвращает разрыв смысловых связей на границах фрагментов.

### 4. Подавление галлюцинаций
* **Пороговая фильтрация (Thresholding):** если $\max(\text{Score}) < T_{\text{threshold}}$ (настраивается в UI, по умолчанию `35%`), генерация отменяется до вызова LLM.
* **Низкая температура сэмплирования:** генерация выполняется с параметрами `temperature = 0.1` и `top_p = 0.9`, что минимизирует стохастичность выбора токенов и удерживает модель строго в рамках переданного контекста.

## Схема базы данных (PostgreSQL)

1. **`knowledge_chunks`** — хранилище фрагментов документов и векторов:
   * `id` (`SERIAL PRIMARY KEY`) — уникальный идентификатор блока.
   * `collection` (`TEXT`) — идентификатор рабочего пространства (изоляция пулов документов).
   * `filename`, `file_ext`, `chunk_index` — метаданные файла и порядковый номер фрагмента.
   * `content` (`TEXT`) — очищенный текст блока.
   * `char_count`, `word_count` (`INT`) — метрики объёма для аналитики.
   * `embedding` (`vector(768)`) — векторное представление блока.
   * `created_at` (`TIMESTAMP`) — время индексации.

2. **`chat_history`** — постоянное хранилище диалогов:
   * `id` (`SERIAL PRIMARY KEY`) — идентификатор сообщения.
   * `collection` (`TEXT`) — привязка ветки диалога к рабочему пространству.
   * `role` (`TEXT`) — роль отправителя (`user` / `assistant`).
   * `content` (`TEXT`) — текст сообщения.
   * `sources` (`JSONB`) — массив использованных первоисточников и их метрик сходства.
   * `created_at` (`TIMESTAMP`) — время отправки.

## Инструкция по развёртыванию и запуску

### 1. Подготовка окружения
Клонируйте репозиторий и создайте файл переменных окружения `.env` в корневой директории:

```bash
git clone <URL_вашего_репозитория> second-brain
cd second-brain

cat << 'EOF' > .env
POSTGRES_USER=brain_user
POSTGRES_PASSWORD=brain_pass
POSTGRES_DB=second_brain
EOF
```

### 2. Запуск контейнеров
Соберите образ приложения и запустите все сервисы в фоновом режиме:

```bash
docker compose up -d --build
```

Проверка статуса контейнеров:
```bash
docker ps
```

### 3. Загрузка весов нейросетей в Ollama
Выполняется однократно (веса сохраняются в локальную директорию `./ollama_models`):

```bash
# Модель для векторизации текста (обязательно)
docker exec -it sb_ollama ollama pull nomic-embed-text

# Генеративные языковые модели (основная и облегчённая)
docker exec -it sb_ollama ollama pull qwen2.5:3b
docker exec -it sb_ollama ollama pull qwen2.5:0.5b
```

Проверка установленных моделей:
```bash
docker exec -it sb_ollama ollama list
```

### 4. Доступ к интерфейсу
После запуска контейнеров веб-интерфейс доступен в браузере по адресу:
`http://localhost:8501`

API сервера моделей Ollama доступен на порту:
`http://localhost:11434`
